# Security policy

## Status and supported versions

The repository currently contains a design baseline and a bootstrap workspace (no measurement code), not a released security product. No supported production version is declared. Releases must publish their supported-version policy and known limitations before adoption.

## Reporting

Do not open a public issue containing sensitive data, exploit payloads tied to protected execution, private logs, or credentials. While private, contact a repository maintainer through an existing private channel. Once available, use GitHub's private vulnerability reporting. Maintainers must configure and document a verified private reporting channel before making the repository public. No response-time promise is established yet.

Provide affected revision, impact, prerequisites, and a minimal synthetic reproduction. Never send real personal data or active/revoked credentials as a test case.

## Threat model

Inputs, generated variants, scanner output, adapter packages, and run configuration are untrusted. A malicious scanner can read its supplied inputs, emit sensitive bytes in errors, consume resources, spawn children, or attempt network access. A scanner shim is executable code, not a harmless parser.

Protected execution also faces leakage through case identities, rare strata, raw hashes, timing, repeated queries, and overly detailed failures. These risks require custodian controls beyond engine implementation.

## Required controls

- Validate contracts, offset bounds, path containment, counts, output sizes, and supported versions before scoring.
- Reject absolute/traversal paths, unexpected symlinks, archive escapes, and mismatched replay identities.
- Use fixed executable paths and structured arguments; never evaluate shell text from a corpus or scanner response.
- Pin scanner/adapter identities and verify digests. Installation/build steps use reviewed dependency and network policies.
- Bound process fan-out, memory, time, buffered output, and temporary storage; cancel descendants as supported by the runner.
- Separate scanner errors from successful scans with no findings. Use sanitized reason codes; raw stdout/stderr never appears in public artifacts.
- Use restricted scratch permissions and deterministic cleanup. Persistent artifacts require an explicit output classification and owner.

Rust memory safety does not provide OS isolation. The runner must enforce network, filesystem, process, and credential boundaries. A `network=off` manifest field is not enforcement evidence by itself.

## Delivery-surface boundaries

State as of bootstrap: only the CI and dependency controls in the next list are implemented; the rest is proposed.

- Implemented: CI uses `permissions: contents: read`, no secrets, no benchmark or scanner checkout, third-party actions pinned by full commit SHA, and `--locked` builds. A test guards `pii-eval-contracts` and `pii-eval-kernel` against unreviewed, process, and network dependencies. First-party crates forbid `unsafe`. These are repository hygiene controls, not an assurance that the future engine is secure.
- Implemented (P6, [ADR 0006](docs/adr/0006-scanner-adapter-boundary.md)): the process adapter runs a fixed absolute executable with structured arguments, a cleared environment plus a fixed allowlist, a closed configuration, SHA-256 verification of the shim and scanner files before spawn, bounded output lines, per-call timeouts and counted-and-discarded stderr, and reports every failure as a distinct sanitized state. This is not OS isolation: descendant cleanup, resource limits, network/filesystem isolation and read-only installs for the run belong to the executor (P7) and the custodian; a pinned file can still be swapped between verification and use.
- Implemented (P7, [ADR 0009](docs/adr/0009-bounded-execution-and-artifact-writing.md)): a bounded executor with a worker cap, deadlines, a fresh process per pass and realm, process-group cleanup of the whole scanner tree on timeout, cancel, crash, limit and drop, sampled memory and scratch limits, private scratch directories, and a validated atomic artifact writer (mode 0600, no overwrite by default, no symlink targets, commit marker last) that runs the accounting verifier on every artifact. **This is process hygiene, not a sandbox**: a hostile scanner can leave its process group, use the network and read what the evaluator's user can read, memory is sampled rather than capped, nothing is cleaned if the evaluator itself is killed, and Windows has no tree cleanup. Containment remains the custodian's.
- Implemented (P8, [ADR 0010](docs/adr/0010-standalone-cli-workflows.md), [docs/cli.md](docs/cli.md)): the CLI validates every identity before launching anything (digest pins, engine, protocol, run class, product, manifest-to-snapshot binding, the adapter-derived scanner plan against the manifest, a preflight hash of every pinned artifact), refuses a protected run without a valid custodian job context before it reads any input and confines protected inputs and outputs to the context's roots (the context grants no access and is not an authorization), turns SIGINT and SIGTERM into cancellation with process-tree cleanup, never reports a failed scanner as success (exit 5), and prints only fixed-vocabulary diagnostics (no input text, values, paths, findings or scanner output) with one JSON summary line on stdout. Not provided: a signature or owner check of the job context, isolation, and tree cleanup after a second signal or a killed CLI.
- Implemented as a library (P11, [ADR 0011](docs/adr/0011-internal-github-app.md), [docs/github-app.md](docs/github-app.md); no App is registered or deployed and the HTTP/GitHub transport is not built): the service core verifies HMAC-SHA256 signatures over the raw body in constant time after a size cap and before any parsing, rejects replayed deliveries, authorizes by numeric installation, repository and actor ids from a deployment-owned allowlist (a comment or label alone grants nothing), binds jobs to immutable commit and profile identities, runs only pinned public synthetic profiles on a bounded worker pool, routes protected profiles to a custodian interface without ever running or authorizing them, drops results for stale heads, and publishes only fixed-template, validated, ASCII Check summaries. Secrets are never part of a job specification. The production runner starts the worker as a separate process with a scrubbed environment and no inherited descriptors, but only the deployment can run it as another OS user or in a container; the in-process runner is for tests and development only (docs/github-app.md). The statement below remains the requirement for the deployed App.
- Implemented (P12, [ADR 0014](docs/adr/0014-custodian-boundary-and-consumer-contract.md), [docs/custodian-boundary.md](docs/custodian-boundary.md)): the engine holds no custody state (no budget, approval, expiry, revocation, signature or ledger field exists in any engine document) and has no publication path for a protected population; the public artifact schema cannot represent one; a tripwire test scans the committed documents for protected populations, ledger field names, key material and custodian internal tags (it is not a history scan). A reference consumer (`examples/consumer/`, standard library only) verifies digests and exact pins, refuses stale, wrong and internal artifacts and never pools populations. The custodian in the round-trip tests is a stub; no custodian code, sandbox, signature or transport was exercised, and the worker protocol is spoken only by `worker-job` (next item), which refuses in a production build.
- Implemented (worker-job, [ADR 0015](docs/adr/0015-worker-job-launcher-and-contract-adapters.md), [docs/worker-job.md](docs/worker-job.md)): `pii-eval worker-job` verifies the custodian's staged world before it reads any protected entry (regular unaliased files, each SHA-256 against its pin, the bundle digest and the package tree digest as two separate typed digests, a strict bounded bundle reader that refuses path traversal, absolute and backslash paths, control characters, duplicates and over-limit archives), reads entries as flat bounded files, runs the same bounded pipeline as `run` writing only under the scratch directory, prints one closed result document of at most 64 KiB and never prints a value, path, entry name or scanner output. Every undecided item of the contract is an adapter with a status; **a production build runs none of them and refuses with `contract-not-final` before reading anything**, there is no flag, environment variable or configuration field that selects a test adapter, and CI fails the engine build if the test adapters (marker `pii-eval-worker-test-adapters`) are in the binary. The artifact CI is a delivery path for the binary, not a sandbox, and protected evaluation never runs in GitHub Actions. A REPLICA bubblewrap sandbox (built from the custodian's launcher argument vector) ran the whole flow in CI with a real Node runtime and synthetic data (job `worker-flow`, docs/worker-job.md); no production-host isolation, no custodian code and no real protected data were exercised, and the custodian-side checks in the tests are a replica.
- Proposed (deployment): a thin internal GitHub App must hold only the minimum repository permissions for requests and Checks, hold no corpus, protected input, custody state, or measurement logic, accept only validated request fields, and post sanitized reason codes and aggregates that the custodian or public policy allows. App credentials are not available to the scanner execution environment.
- Proposed: protected runs execute only inside a custodian-controlled environment; the engine's output is internal until the custodian projects it. The App never reads the private audit ledger.
- Public review records and private audit records are separate classes; neither is a substitute for the other, and a GitHub status is not an authorization decision.

## Data policy

Ordinary development, fixtures, tests, examples, and public CI use safe synthetic/public-test data only. Public synthetic values must never be used in production systems. Real customer data, production logs, and real credentials are prohibited in this repository.

Protected synthetic inputs may be measured only through an authorized custodian run. Future use of real personal data is out of scope and requires a separate reviewed data-governance design before ingestion.

Internal output is not automatically public. Public projection must be allowlisted and validated independently; protected projections exclude input text, seeds, raw findings/ranges, individual case IDs, value hashes, raw errors, and private paths. Population commitments intended for public use must come from the custodian's opaque release identity policy rather than unsalted low-entropy value hashes.

## Integrity and release

Bind candidate bytes, scanner configuration, corpus, adapter, and engine to every run. Verify candidate identity before and after execution where the execution boundary allows mutation. A signature proves provenance under its trust model, not correctness or independence.

Internal engine artifacts: CI publishes the engine as a GitHub Actions workflow artifact for use by other workflows ([docs/ci-artifacts.md](docs/ci-artifacts.md)). It is internal only (readable by people with read access to this repository for 30 days on `main`, 3 days elsewhere), unsigned and unattested, and not a release. Workflows pin every action by commit SHA, declare least-privilege `permissions`, receive untrusted input only through `env:`, and are checked by `tools/ci/workflow-policy.mjs`; artifacts must never carry protected material, and the CLI refuses a protected run without a custodian job context.

Publish no accuracy/speed/security claim without pinned evidence and stated limitations. Before public release, configure private reporting, scan repository history/assets/logs (the license is MIT, see `LICENSE`), review third-party redistribution, and demonstrate publication guards. Keep synthetic measurement and candidate/internal results correctly labeled.
